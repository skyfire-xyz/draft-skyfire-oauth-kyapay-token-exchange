KYAPay Token Exchange

Abstract

This specification describes how KYAPay tokens can be exchanged for OAuth access tokens to dynamically grant agents access to resources they need to accomplish their mission.¶

1. Introduction

KYAPay tokens [I-D.skyfire-oauth-kyapay-token] are used by agents to identify themselves, the principal they are acting on behalf of, their payment capabilities, their authorized scope of action or mission, and their intended audience. Agents may need access to resources to accomplish their mission. This specification describes how an agent can present a KYAPay token to obtain an OAuth access token granting access to a resource that it needs to accomplish its mission.¶

1.1. Use Cases for KYAPay Token Exchange

Enabling agents to create accounts and/or log in to accounts on behalf of their human principals is a design goal. To achieve this, systems can utilize a token exchange workflow. In this process, a Security Token Service (STS), Identity Provider (IdP), or OAuth Authorization Server verifies incoming KYA tokens and extracts claims associated with the human principal, such as email addresses. The authorization server then performs a token exchange, swapping the KYA token for a standard OAuth Access Token, which the agent subsequently uses to interact with the target service. Crucially, this architecture allows the service to know that the agent is acting on behalf of the user, making it possible to differentiate between direct, human-present sessions and human-initiated, agentic sessions for authorization, auditing, and security purposes.¶

One example use case is to exchange a KYAPay token for an OAuth access token for a Model Context Protocol [MCP] service when the agent needs to use the MCP service to accomplish its goals.¶

Early production deployments of KYAPay tokens are described at https://kyapay.org.¶

3. KYAPay Token Exchange

The KYAPay token contains identifying information for both the principal on whose behalf the request is being made (in the Human Identity (hid) claim) and the agent that is authorized to act on behalf of the principal (in the Agent Platform Identity (apd) claim and the Agent Identity (aid) claim).¶

This specification defines two methods of exchanging KYAPay tokens for access tokens: a direct method and a method using a Client ID Metadata Document (CIMD) [I-D.ietf-oauth-client-id-metadata-document]. It also defines an OAuth authorization server metadata parameter enabling authorization servers to declare that KYAPay Token Exchange is supported.¶

The steps when successfully exchanging a KYAPay token for an access token and using it with the protected resource are:¶

  1. The client retrieves the OAuth protected resource metadata document [RFC9728].¶

  2. The client determines from the resource metadata what authorization server(s) can be used for the token exchange.¶

  3. The client chooses an authorization server and retrieves its metadata [RFC8414].¶

  4. The client determines from the authorization server metadata whether the authorization server supports KYAPay Token Exchange, per Section 6. It also may be able to determine if the authorization server accepts tokens from specific KYAPay token issuers.¶

  5. The client makes a token exchange [RFC8693] request to the authorization server, passing the KYAPay token as the subject_token value, the subject_token_type value of urn:ietf:params:oauth:token-type:kyapay, and passing the resource identifier [RFC8707] as the "resource" value.¶

  6. The authorization server returns an access token for the resource to the client using information from the KYAPay token to create the access token. Note that this may be a bearer access token [RFC6750] or a DPoP-bound access token [RFC9449]. The access token will contain or reference sufficient information for the protected resource to be able to provision access for the client, which may include dynamic account creation.¶

  7. The client uses the access token to make an HTTP resource request to the resource.¶

  8. The resource responds to the resource request providing the requested information.¶

Note that the ability to use information in the KYAPay token to dynamically provision access to the resource by the agent is critical to enable seamless agentic access to resources for the user. This obviates the need to pre-provision an account for the user at every resource that their agent might access -- a process that would not scale.¶

4. Direct KYAPay Token Exchange Method

The direct KYAPay Token Exchange method uses a Client Identifier that is constructed directly from information in the KYA Token. Its value contains the token issuer, the token originator, the agent platform identifier, and the agent identity identifier. Specifically, it is the string concatenation of - the string literal "kyapay:", - the iss claim value, - the string literal "|", - the ori claim value, - the string literal "|", - the apd claim's id value, - the string literal "|", and - the aid claim's id value.¶

If the KYAPay token has no ori claim, or no apd claim, the corresponding part is the empty string, so the Client ID always has four parts separated by "|".¶

An example such Client ID value is:¶

kyapay:https://app.skyfire.xyz|https://app.skyfire.xyz|a283ced5-95be-4abe-81aa-51552e8876ad|7d889702-7b6a-46cb-9bdd-10e83d17b18d
¶

This requires the authorization server to recognize and accept these Client IDs without client pre-registration (as described in Section 2 of [RFC6749]) or dynamic client registration [RFC7591]. There is precedent for authorization servers using non-pre-registered clients based on the syntax of their Client Identifiers; the Client ID Metadata Document (CIMD) [I-D.ietf-oauth-client-id-metadata-document] specification uses unregistered Client IDs, the OpenID Federation [OpenID.Federation] specification uses unregistered Client IDs, and the OpenID for Verifiable Presentations [OpenID4VP] specification uses unregistered Client IDs. The OpenID4VP specification also uses Client ID prefixes, as this specification does.¶

The token exchange uses [RFC8693] and is performed as follows:¶

  • The "none" client authentication method [RFC7591] is used.¶

  • An HTTP POST is made to the authorization server's token endpoint.¶

  • The grant_type value is urn:ietf:params:oauth:grant-type:token-exchange.¶

  • The client_id value is the Client ID constructed as described above.¶

  • The subject_token value is the KYAPay token being exchanged.¶

  • The subject_token_type value is urn:ietf:params:oauth:token-type:kyapay.¶

  • The resource value is the URL of the protected resource that the resulting token is intended for.¶

  • The requested_token_type parameter MAY be included; if included, its value is urn:ietf:params:oauth:token-type:access_token.¶

  • No actor_token or actor_token_type parameters are included.¶

The following is a non-normative example of a POST request to perform a direct KYAPay token exchange for an access token:¶

POST /token HTTP/1.1
Host: as.example.com
Content-Type: application/x-www-form-urlencoded

grant_type=urn:ietf:params:oauth:grant-type:token-exchange
&client_id=kyapay:https://app.skyfire.xyz|https://app.skyfire.xyz|a283ced5-95be-4abe-81aa-51552e8876ad|7d889702-7b6a-46cb-9bdd-10e83d17b18d
&subject_token=*KYAPay Token*
&subject_token_type=urn:ietf:params:oauth:token-type:kyapay
&resource=https://mcp.acme.example/
&requested_token_type=urn:ietf:params:oauth:token-type:access_token
¶

5. KYAPay Token Exchange Method using Client ID Metadata Document (CIMD)

This section describes a KYAPay token exchange method using a Client ID Metadata Document (CIMD) [I-D.ietf-oauth-client-id-metadata-document]. This method uses the CIMD URL as the Client ID.¶

As described in Section 8.2 of [I-D.ietf-oauth-client-id-metadata-document] (Client Authentication), clients that are capable of maintaining private key material and performing client authentication SHOULD do so with an acceptable method, such as the private_key_jwt [OpenID.Core] client authentication method. Otherwise, the "none" client authentication method [RFC7591] is used, and the client_id parameter is the CIMD URL.¶

The token exchange uses [RFC8693] and is performed as follows:¶

  • An HTTP POST is made to the authorization server's token endpoint.¶

  • The grant_type value is urn:ietf:params:oauth:grant-type:token-exchange.¶

  • The subject_token value is the KYAPay token being exchanged.¶

  • The subject_token_type value is urn:ietf:params:oauth:token-type:kyapay.¶

  • The resource value is the URL of the protected resource that the resulting token is intended for.¶

  • The requested_token_type parameter MAY be included; if included, its value is urn:ietf:params:oauth:token-type:access_token.¶

  • No actor_token or actor_token_type parameters are included.¶

The following is a non-normative example of a POST request by a CIMD client using the private_key_jwt client authentication method to perform a KYAPay token exchange for an access token:¶

POST /token HTTP/1.1
Host: as.example.com
Content-Type: application/x-www-form-urlencoded

grant_type=urn:ietf:params:oauth:grant-type:token-exchange
&subject_token=*KYAPay Token*
&subject_token_type=urn:ietf:params:oauth:token-type:kyapay
&resource=https://mcp.acme.example/
&requested_token_type=urn:ietf:params:oauth:token-type:access_token
&client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer
&client_assertion=*JWT whose iss and sub are the CIMD URL*
¶

6. Authorization Server Metadata

An authorization server declares support for KYAPay token exchange by including a kyapay_issuers_supported authorization server metadata parameter [RFC8414]. The definition of this parameter is:¶

kyapay_issuers_supported:

OPTIONAL. JSON array containing a list of issuer identifiers of KYAPay token issuers, as specified in [I-D.skyfire-oauth-kyapay-token], that can be used with this authorization server. Authorization servers MAY choose not to advertise some supported token issuers, even when this parameter is used. In some use cases, the set of token issuers will not be enumerable. The array MAY be empty.¶

An authorization server that includes this parameter MUST also include urn:ietf:params:oauth:grant-type:token-exchange in grant_types_supported.¶

7. KYAPay Token Example

An example decoded set of JWT Header Parameters for a KYAPay token is:¶

{
  "alg": "ES256",
  "kid": "BEDD-0",
  "typ": "kya+jwt"
}
¶

{
  "env": "production",

    "email": "example@skyfire.xyz",
    "verifier": "https://app.skyfire.xyz",

The KYAPay token is used as the subject_token value for the token exchange.¶

8. Security Considerations

The security considerations defined in [I-D.skyfire-oauth-kyapay-token] and [RFC7523] apply to this specification.¶

9. Privacy Considerations

The privacy considerations defined in [I-D.skyfire-oauth-kyapay-token] and [RFC7523] apply to this specification.¶

The kyapay_issuers_supported value may disclose a set of KYAPay token issuers that the authorization server trusts. Clients may need to know, before making a request, whether a KYAPay token they hold or can obtain will be accepted. Deployments that consider their issuer relationships sensitive should take this into account before publishing the list.¶
